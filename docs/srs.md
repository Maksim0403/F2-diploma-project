# Software Requirements Specification (SRS)

## Pet Care System

**Назва проєкту:** Розроблення мобільного застосунку для догляду за домашніми тваринами на основі подієво-орієнтованої архітектури (Event Sourcing)

**Версія:** 1.0  
**Дата:** 03.11.2026  
**Статус:** Робоча специфікація для архітектурного проєктування

## 1. Вступ

### 1.1. Призначення документа

Цей документ визначає функціональні та нефункціональні вимоги до Pet Care System. Специфікація використовується як основа для проєктування архітектури, реалізації програмних компонентів і подальшого тестування системи.

### 1.2. Мета системи

Метою проєкту є розроблення мобільного застосунку, який допомагає власникам домашніх тварин зберігати інформацію про улюбленців, вести історію їхнього здоров'я, планувати нагадування та переглядати географічне розташування.

### 1.3. Межі системи

Система складається з Android-клієнта та серверної частини, представленої такими сервісами:

- **Pet Service** — керування профілями тварин та історією їхнього здоров'я.
- **Reminder Service** — створення та оброблення нагадувань.
- **Geo Service** — отримання та збереження географічних координат.

Для обміну подіями між сервісами використовується Apache Kafka. Основне сховище даних — PostgreSQL. Redis передбачений для допоміжного кешування. Push-сповіщення реалізуються за допомогою Firebase Cloud Messaging.

### 1.4. Терміни та скорочення

| Термін | Опис |

## 2. Загальний опис

### 2.1. Класи користувачів

| Користувач | Роль |
|---|---|
| Власник тварини | Основний користувач мобільного застосунку |
| Співвласник | Користувач із доступом до спільної інформації про тварину |
| Ветеринар | Перегляд наданої власником інформації про здоров'я тварини |
| Адміністратор | Адміністративне обслуговування системи |

### 2.2. Загальні припущення та обмеження

- Клієнтська частина системи розробляється для Android.
- Основна взаємодія користувача із системою відбувається через мобільний застосунок.
- Серверна частина складається з окремих сервісів із визначеними зонами відповідальності.
- Pet Service використовує Event Sourcing.
- Reminder Service і Geo Service використовують традиційне збереження поточного стану даних.
- Для міжсервісної асинхронної взаємодії використовується Apache Kafka.
- Початкова реалізація геолокації передбачає використання GPS Simulator, а не фізичного GPS-трекера.
- Система не замінює професійну ветеринарну консультацію.

## 4. Нефункціональні вимоги

### 4.1. Продуктивність

- **SRS-NFR-01.** Основні операції перегляду та редагування даних повинні виконуватися без невиправданих затримок за нормального навантаження.
- **SRS-NFR-02.** Архітектура повинна дозволяти незалежне масштабування серверних сервісів.
- **SRS-NFR-03.** Оброблення асинхронних подій не повинно блокувати основні синхронні операції користувача.

### 4.2. Надійність

- **SRS-NFR-04.** Система повинна зберігати цілісність даних під час виконання операцій запису.
- **SRS-NFR-05.** Механізм Transactional Outbox повинен запобігати втраті події між фіксацією змін у базі даних та її публікацією в брокер.
- **SRS-NFR-06.** Оброблення повідомлень повинно враховувати можливість повторної доставки.
- **SRS-NFR-07.** Помилки взаємодії із зовнішніми сервісами повинні оброблятися без аварійного завершення всієї системи.

### 4.3. Безпека

- **SRS-NFR-08.** Передавання даних між клієнтом і сервером повинно здійснюватися через захищений канал зв'язку.
- **SRS-NFR-09.** Система повинна перевіряти права доступу перед виконанням операцій із даними.
- **SRS-NFR-10.** Секрети та облікові дані підключення не повинні зберігатися у відкритому вигляді в репозиторії.
- **SRS-NFR-11.** Система повинна обмежувати доступ до персональних даних відповідно до ролі користувача.

### 4.4. Супроводжуваність та розширюваність

- **SRS-NFR-12.** Серверні сервіси повинні мати чітко визначені межі відповідальності.
- **SRS-NFR-13.** Код повинен підтримувати модульну структуру та розділення бізнес-логіки й інфраструктурних деталей.
- **SRS-NFR-14.** Формат доменних подій повинен передбачати можливість версіонування.
- **SRS-NFR-15.** Архітектура повинна допускати додавання нових сервісів та споживачів подій без суттєвої зміни наявних компонентів.

### 4.5. Сумісність та зручність використання

- **SRS-NFR-16.** Мобільний клієнт повинен бути розроблений для платформи Android.
- **SRS-NFR-17.** Інтерфейс повинен забезпечувати зрозумілий доступ до профілів тварин, медичної історії та нагадувань.
- **SRS-NFR-18.** Часові значення повинні оброблятися з урахуванням часових поясів; для початкової конфігурації використовується `Europe/Kyiv`.

## 5. Зовнішні інтерфейси

### 5.1. Користувацький інтерфейс

Взаємодія з системою здійснюється через Android-застосунок, розроблений із використанням Kotlin та Jetpack Compose.

### 5.2. Програмні інтерфейси

- REST API — синхронна взаємодія мобільного клієнта із серверними сервісами.
- Apache Kafka — асинхронний обмін доменними подіями між сервісами.
- Firebase Cloud Messaging — доставка push-сповіщень.
- Google Maps SDK — відображення географічних координат.

### 5.3. Інтерфейси зберігання даних

- PostgreSQL — основне реляційне сховище.
- Event Store — збереження послідовності доменних подій Pet Service.
- Outbox — збереження подій, що очікують публікації.
- Redis — допоміжне кешування.
