# ADR-001: Вибір брокера повідомлень для міжсервісної взаємодії

- **Статус:** Approved
- **Дата:** 03.11.2026
- **Рішення:** Apache Kafka
- **Пов'язані документи:** [SRS](../srs.md), [Архітектура системи](../2_design.md)

## 1. Контекст

Pet Care System складається з трьох серверних сервісів: Pet Service, Reminder Service та Geo Service. Сервіси мають взаємодіяти між собою, не створюючи надмірної залежності один від одного.

Pet Service використовує Event Sourcing. Зміни предметної області зберігаються як послідовність доменних подій. Інші сервіси повинні мати можливість незалежно отримувати та обробляти релевантні події.

Для реалізації асинхронної взаємодії необхідно обрати брокер повідомлень. Розглянуто два варіанти: Apache Kafka та RabbitMQ.

Ключові критерії вибору:

- підтримка асинхронного обміну повідомленнями;
- можливість повторного читання повідомлень;
- підтримка незалежних споживачів;
- збереження порядку повідомлень у межах визначеного потоку;
- надійність публікації;
- складність розгортання та супроводу;
- відповідність архітектурі Event Sourcing.

## 2. Розглянуті альтернативи

### 2.1. Apache Kafka

Apache Kafka — розподілена платформа потокової передачі подій, яка зберігає повідомлення у вигляді журналу з можливістю налаштування строку зберігання.

**Переваги:**

- збереження потоку повідомлень відповідно до політики retention;
- незалежне читання подій різними consumer groups;
- можливість повторного читання повідомлень за допомогою offsets;
- підтримка partitioning;
- збереження порядку повідомлень у межах однієї partition;
- відповідність моделі подієво-орієнтованої архітектури.

**Недоліки:**

- складніше розгортання та адміністрування порівняно з простішими брокерами;
- додаткові вимоги до оперативної пам'яті, процесорного часу та дискового простору;
- необхідність моніторингу стану брокера, partitions та consumer lag;
- додаткові витрати на інтеграційне тестування та підтримку інфраструктури.

### 2.2. RabbitMQ

RabbitMQ — брокер повідомлень, який використовує exchanges, queues та bindings для маршрутизації повідомлень між виробниками і споживачами.

**Переваги:**

- гнучка маршрутизація повідомлень;
- підтримка acknowledgements та publisher confirms;
- зрозуміла модель черг;
- можливість налаштування повторної доставки;
- підтримка RabbitMQ Streams, що також забезпечують збереження повідомлень та можливість повторного читання.

**Недоліки:**

- класична модель черг орієнтована передусім на доставку та оброблення повідомлень, а не на загальний журнал подій;
- для сценаріїв збереження потоків і повторного читання необхідно окремо враховувати можливості RabbitMQ Streams;
- модель роботи зі споживачами та повторним читанням відрізняється від Kafka і потребує окремого проєктування.

## 3. Прийняте рішення

Для міжсервісної асинхронної взаємодії Pet Care System обрано **Apache Kafka**.

Основні причини:

1. Модель журналу подій Kafka відповідає подієво-орієнтованій архітектурі системи.
2. Незалежні consumer groups дозволяють різним сервісам обробляти один потік подій незалежно.
3. Offsets дозволяють керувати позицією читання та повторно обробляти збережені повідомлення.
4. Partitioning дає змогу зберігати порядок повідомлень для однієї сутності за умови використання стабільного ключа, наприклад `pet_id`.

Вибір не означає, що Kafka є кращою за RabbitMQ для всіх сценаріїв. Для невеликої системи RabbitMQ також може бути цілком обґрунтованим рішенням, зокрема з використанням Streams.

У цьому проєкті перевага надається моделі збереженого потоку подій та незалежного читання повідомлень.

## 4. Наслідки рішення

### 4.1. Позитивні наслідки

- Підтримка подієво-орієнтованої взаємодії між сервісами.
- Можливість підключення нових споживачів без прямої зміни Pet Service.
- Можливість повторного читання подій у межах політики зберігання.
- Незалежне масштабування споживачів.
- Можливість зберігати порядок подій для однієї сутності в межах partition.

### 4.2. Негативні наслідки та компроміси

- Kafka збільшує складність локального розгортання та супроводу системи.
- Виникають додаткові витрати ресурсів: CPU, RAM, дисковий простір і мережевий трафік.
- Потрібно налаштовувати topics, partitions, retention та моніторинг.
- Інтеграційні тести повинні враховувати доступність брокера та повторні підключення.
- Виникає залежність від конкретної технології брокера.
- Порядок повідомлень гарантується лише в межах однієї partition, а не глобально.
- Повторна доставка повідомлень вимагає ідемпотентної обробки споживачами.

### 4.3. Фінансові та операційні аспекти

Для локального прототипу Kafka запускається в Docker Compose. Розгортання високодоступного production-кластера не є вимогою поточного етапу проєкту.

Фактичні грошові витрати не фіксуються, оскільки не визначено хмарного провайдера, тарифу та очікуваного навантаження. Водночас враховуються витрати на обчислювальні ресурси, зберігання даних, моніторинг і супровід.

## 5. Надійність публікації: Transactional Outbox

Для забезпечення узгодженості між збереженням доменних подій та їх публікацією в Kafka використовується патерн Transactional Outbox.

Під час оброблення команди Pet Service у межах однієї транзакції PostgreSQL:

1. Зберігає нову доменну подію в Event Store.
2. Створює відповідний запис у таблиці Outbox.
3. Підтверджує транзакцію лише після успішного виконання обох операцій.

Окремий Outbox Publisher Worker отримує непубліковані записи та передає їх до Kafka.

Після підтвердження публікації запис позначається як оброблений. Якщо публікація не вдалася, повідомлення може бути повторно надіслане.

Модель доставки — at-least-once. Тому споживачі повинні забезпечувати ідемпотентність оброблення.

Для збереження порядку подій однієї тварини як Kafka message key використовується `pet_id`.

## 6. Управління ризиками

| Ризик | Спосіб мінімізації |
|---|---|
| Недоступність Kafka | Повторні спроби публікації та збереження повідомлень у Outbox |
| Повторна доставка | Ідемпотентність споживачів |
| Затримка оброблення | Моніторинг consumer lag |
| Помилки серіалізації | Валідація та версіонування схем подій |
| Надмірне накопичення повідомлень | Політика retention та контроль дискового простору |
| Залежність від брокера | Ізоляція інтеграції через порти й адаптери |
| Складність локального середовища | Використання Docker Compose та автоматизованих інтеграційних тестів |

## 7. Умови перегляду рішення

Рішення може бути переглянуте, якщо:

- вимоги до системи зміняться на користь маршрутизації повідомлень через складні правила exchanges;
- використання Kafka створюватиме непропорційно високі витрати на супровід;
- зміниться модель взаємодії між сервісами;
- результати практичного навантажувального тестування покажуть, що обрана конфігурація не відповідає вимогам.

## 8. Висновок

Apache Kafka обрано через відповідність моделі збереження та повторного читання подій, незалежність споживачів і можливість організації подієвої взаємодії між сервісами.

Основним компромісом є більша складність інфраструктури та її супроводу порівняно з простішими сценаріями використання RabbitMQ. Для поточного прототипу цей компроміс вважається прийнятним.
